## 2. V0.16 已有能力

V0.16 的统一管线为：

`SceneRecipe → Generator → SceneGraph → LayerComposer → LightingPass → SceneEvaluator`

四种专用生成器：
- Crystal：Poisson Disk Sampling、构图锚点、参数化晶体。
- Spore：Poisson 群落布局、Bézier 菌体、递归菌丝分枝。
- Fossil：Catmull–Rom 脊柱、椎骨采样、法线方向肋骨。
- City：确定性 Shape Grammar、拱门、塔楼、平台、桥梁。

`SceneRecipe v1` 当前参数包括 `scale`、`density`、`rough`、`glow`、`particles`、`water`，以及 `biome`、`seed`、`viewport`。

V0.16 的回归测试记录：
- 四种景观 × 8 个种子：32/32 静态像素确定性。
- 四种景观 × 6 个参数：24/24 参数改变可见输出。
- 静态帧重复稳定：4/4。
- 动态层随时间变化：4/4。
- PNG / Recipe JSON 导出、自定义生成器注册、390px 视口检查通过。
- 页面异常 0。
- 受控 Chromium 离屏生成+绘制中位耗时约 1.3–1.6ms；不能解释为真实设备 FPS。

必须保留这些测试的边界：它们证明确定性、参数响应和基本工程正确性，不证明场景达到人类审美标准。

## 3. V0.16 当前 SceneEvaluator 的真实能力与缺口

已核对当前实现，`SceneEvaluator.evaluate()` 主要计算：
- `structureCount`：生成器统计的结构数量。
- `layerCount`：图层数量。
- `colorBuckets`：以 5-bit RGB 桶采样得到的颜色桶数量。
- `luminanceSD`：稀疏采样像素的亮度标准差。
- `sampleCount`：像素采样数量。

这只是工程遥测和非常粗略的图像统计，不是审美分数。

当前生成器的 `objects` 主要包含 `count`、`lights`、`particles`、`type`；图层主要是带绘制闭包的 `{id, depth, draw}`。缺少完整、统一的语义物件目录，例如物件角色、包围盒、面积、焦点权重、遮挡关系和像素掩码。因此 V0.17 的首要工程任务不是直接写一个大评分公式，而是先补齐可解释的场景元数据。

## 4. 核心研究判断

**不要把“好看”压缩成一个未经验证的总分。**

建议把 V0.17 做成多层评价系统：

1. 硬性正确性：无空白帧、无 NaN、无脚本错误、无无效图层、导出有效。
2. 可解释的视觉代理指标：构图、焦点、层次、色彩、明暗、遮挡、密度、可读性。
3. 生成器能力指标：种子多样性、参数可控性、生成时间。
4. 人类偏好验证：盲测 A/B 或成对比较。
5. 可选视觉语言模型意见：作为辅助诊断，不得单独决定通过或合并。

V0.17 先输出分项报告和缺陷解释，不发布“AI 审美 92 分”一类没有校准依据的分数。

## 5. 建议新增的数据契约

### 5.1 VisualSpec（每个景观单独定义）

`VisualSpec` 与 `SceneRecipe` 分离。Recipe 表达“如何生成”，VisualSpec 表达“本主题希望达到什么视觉目标”。

建议字段：
- `specVersion`、`biome`、`referenceId`。
- `focalTargets[]`：归一化中心、区域半径/多边形、重要度、目标物件角色。
- `regions[]`：前景、中景、背景和负空间区域。
- `paletteRoles`：主色、辅色、强调色、暗部、高光及容许色差。
- `hierarchy`：主物件/次物件/细节物件的数量、面积或尺度范围。
- `depthTargets`：不同深度层的对比度、饱和度、尺寸、遮挡与雾化目标。
- `readabilityRules`：玩家轮廓、可交互平台、关键路径的可见性约束。
- `styleRules`：像素网格、整数缩放、边缘清晰度和禁止的平滑处理。

AI 概念图仅作为艺术方向参考，不应被当成逐像素真值。应先人工标注其主体焦点、空间分层、色彩角色和关键地标，再转换成 VisualSpec。

### 5.2 SceneGraph 对象元数据

建议给每个生成对象登记：
`{id, type, role, layerId, depth, bounds, center, area, focalWeight, paletteRole, occlusionGroup, seedKey}`

其中：
- `type`：crystal / mushroom / rib / skull / arch / tower 等。
- `role`：primary / secondary / detail / background / foreground。
- `bounds`：归一化包围盒；必要时提供低分辨率二值 mask。
- `focalWeight`：来自 VisualSpec 或生成器设计的预期重要度。
- `occlusionGroup`：辅助判断遮挡与前后关系。
- `seedKey`：定位对象来自哪个独立随机子流，便于重现问题。

不要求所有对象一开始都保存完整像素 mask。先使用包围盒与角色元数据，确有必要时再对主物件增加低分辨率 mask。

## 6. V0.17 指标体系（建议分项，不直接相加）

### A. 构图与焦点
- 焦点偏移：实际视觉显著性中心与 VisualSpec 目标中心的距离。
- 焦点支配度：目标主物件区域的显著性质量 / 全图显著性质量。
- 主次面积比：主物件、次物件、细节物件的可见面积比例。
- 空间平衡：画面分区视觉质量与预期构图模板的偏差。
- 负空间比例：可读的留白面积是否处于主题允许范围。

第一版优先使用 SceneGraph 元数据、物件包围盒和局部亮度/颜色对比构建可解释代理指标。不要一开始就依赖神经网络 saliency map。

### B. 景深与空间层次
- 前/中/后景可见面积比例。
- 各层平均亮度、饱和度和边缘密度差异。
- 主体遮挡率、错误遮挡率和关键地标可见率。
- 远景尺度递减、对比度递减是否符合主题设定。
- 视差/空间分离：对象层级与位置是否真的形成纵深。

像素风格不应简单用 Gaussian Blur 制造景深；优先使用轮廓、尺度、色彩、对比度、雾层和遮挡差异。

### C. 色彩体系
- 从 RGB 5-bit 桶升级到 OKLab 或 CIELAB 的感知色差统计。
- 主题色覆盖率：各 palette role 在画面中的像素比例。
- 色相分布与 VisualSpec 目标色域的偏差。
- 主辅强调色比例、暗部/高光比例。
- 色彩离散度只作诊断，不能把颜色越多或熵越高视为越好。

### D. 光照与明暗
- 亮度分位数（P10/P50/P90）和动态范围。
- 主焦点与周围背景的局部对比度。
- 高光剪切/过曝比例、黑位压死比例。
- 光源数量、光晕覆盖率、光源与目标物件的对应关系。
- 是否出现多个互相争夺注意力的亮点。

不要单纯最大化亮度标准差；高对比度也可能造成刺眼、脏乱或焦点分散。

### E. 密度、遮挡与可读性
- 网格占用率与局部密度热图。
- 物件包围盒重叠率、主物件被遮挡比例。
- 连通区域数量、碎片化程度。
- 玩家剪影与背景的局部对比度。
- 关键平台/道路/入口的可见性。
- 小于目标像素尺度的细节比例，避免细节噪声。

### F. 多种子多样性
每种景观至少采样 32 个固定种子，构建特征向量：
- 主焦点位置、主物件面积和方向。
- 对象数量与角色分布。
- 颜色直方图/感知色彩特征。
- 前中后景占比。
- 低分辨率轮廓/空间占用特征。

报告 pairwise distance、最近邻距离、特征覆盖范围和重复场景率。多样性不是越大越好：必须同时检查是否偏离主题风格，避免为了差异而产生杂乱场景。

### G. 参数可控性
为每个参数声明预期影响：
- scale：主体尺度或面积变化。
- density：对象密度变化。
- rough：轮廓/形态扰动变化。
- glow：辉光能量/覆盖率变化。
- particles：粒子数量变化。
- water：水面效果强度变化。

通过单参数扰动和局部敏感度测试，检查变化是否可观测、方向是否符合定义，以及是否意外破坏其它指标。不能仅以“PNG 不同”作为参数有效的唯一证据。

### H. 工程性能
分别测量生成器构建、静态图层绘制、动态通道绘制、Evaluator 扫描耗时；报告 median / P90。另记录图像尺寸、采样步长、对象数和内存估计。Chromium 结果不能冒充真实 Android FPS。

## 7. 推荐算法实现顺序

1. **SceneGraph Metadata Registry**：对象角色、bounds、layer、importance、seedKey。
2. **VisualSpec v1**：四种景观各自的目标焦点、色彩、层级、密度与可读性约束。
3. **Raster Analyzer**：Canvas 像素采样、亮度/色彩统计、分区特征。
4. **Composition Evaluator**：焦点偏移、视觉质量分布、主次面积比、负空间。
5. **Depth & Occlusion Evaluator**：层级面积、遮挡率、远景对比与可见性。
6. **Palette & Lighting Evaluator**：OKLab/CIELAB 色差、色彩角色比例、局部对比度和高光剪切。
7. **Diversity & Controllability Evaluator**：32+ seeds、特征空间覆盖、参数敏感性。
8. **Diagnostic Overlay**：焦点热图、密度热图、遮挡框、深度层分区、色彩统计。
9. **Human A/B Review**：固定 seed 的基线与改进版盲测。
10. **Optional ML advisory**：在指标稳定后，试验 CLIP-IQA / NIMA / MUSIQ 等模型，不作为硬门槛。

## 8. 人工验证设计

建议建立小型但可复现的人工审阅集：
- 四种景观，每种 8 个固定种子，共 32 个基础样本。
- 对同一 seed 生成 baseline / candidate 成对图片，随机左右顺序。
- 让评审回答：更喜欢哪张？主体是否突出？空间层次是否清楚？颜色是否协调？细节是否过密？玩家是否可辨认？
- 保存胜负、置信度、缺陷标签和自由评论。
- 报告 pairwise win rate 及置信区间；样本少时明确说明只是探索性结果。
- 若只有项目作者一人审阅，必须标记为作者自评，不能宣称用户研究或人类共识。

## 9. 受控缺陷测试（Evaluator 是否真的有用）

必须人工注入已知缺陷，验证指标能否检测：
1. 删除主晶簇/主菌体/核心塔/头骨：焦点支配度或关键物件覆盖应下降。
2. 删除远景层：景深分层和背景面积指标应报警。
3. 将主题色替换为随机颜色：palette deviation 应增加。
4. 将物件密度提高到过量：重叠率、局部拥挤度应增加。
5. 把粒子和高光集中到非焦点区域：焦点竞争指标应报警。
6. 让前景遮挡矿工或关键平台：玩家/交互可读性应下降。
7. 固定相同参数只改变 seed：确定性与多样性指标应分别正确响应。

这些测试比“程序返回一个分数”更重要，因为它们验证指标是否对目标缺陷敏感。

## 10. 视觉语言模型与传统 IQA 的适用边界

- NIMA（Talebi & Milanfar, 2018）预测人类评分分布，证明可学习图像审美评估的可行性；但 AVA 等训练数据主要是摄影作品，不能直接假定对本项目像素艺术有效。
- MUSIQ（ICCV 2021）用多尺度 Transformer 处理原始尺寸和不同宽高比图像；可作为多尺度 IQA 参考，但它解决的是通用图像质量评价，不等于程序化游戏场景的构图审美。
- CLIP-IQA / “Exploring CLIP for Assessing the Look and Feel of Images”（2022）展示了用正反提示词对比较图像质量与抽象观感的路径；适合作为辅助意见来源。
- 多组 antonym prompt 的可解释 IQA 研究（2023）展示了把锐度、噪声、亮度等属性拆开评估的思路；本项目可借鉴“分属性诊断”，但需重新设计像素场景提示词并人工校准。
- Composition-Aware Image Aesthetics Assessment（WACV 2020）把图像划分为局部区域并建模区域之间的依赖，支持 V0.17 不应只看全图平均颜色/亮度，而应关注局部区域关系。
- PCG Evaluation Survey（FDG 2024）指出 PCG 评价缺少统一共识，并整理了 fitness、metric diversity、expressive range analysis、controllability 和 human-in-the-loop 等类别。
- PCG Benchmark（FDG 2025）明确把生成质量、多样性和可控性作为不同维度；本项目也应分别报告，不能合成一个未校准总分。

## 11. V0.17 第一阶段验收标准

- 四种景观均有版本化 VisualSpec。
- SceneGraph 输出可审计的对象角色和几何元数据。
- VisualReport 输出各项指标、目标范围、诊断原因和建议，不输出未经验证的单一审美总分。
- 七类受控缺陷均有自动化回归用例。
- 四种景观 × 至少 32 seeds 的多样性报告。
- 同一 Recipe 的静态像素可重复；动态层单独测试。
- 参数可控性按预期方向验证。
- 人工 A/B 评价有记录、有样本数、有局限说明。
- 390×844 移动视口、Chromium 页面错误、PNG/JSON 导出测试通过。
- 生成、绘制和评估耗时分别统计 median / P90。
- 不修改 main，不把 V0.17 实验误称为正式游戏集成。

- 先读取 GitHub 仓库最新状态、当前分支、README、V0.16 源码和文档；不要沿用本文件的 SHA 作为最新基线。
